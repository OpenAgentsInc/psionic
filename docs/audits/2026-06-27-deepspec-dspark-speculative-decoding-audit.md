### What DSpark actually is

Speculative decoding pairs a lightweight **draft model** that proposes a block
of `γ` candidate tokens with the full-size **target model** that verifies the
whole block in one forward pass, accepting the longest prefix consistent with
the target distribution (lossless — exact target distribution preserved).
Per-token latency is `L = (T_draft + T_verify) / τ`, where `τ` is accepted
tokens per cycle. Speedup comes from three levers: draft faster, draft better
(raise `τ`), or verify smarter.

DSpark contributes two complementary mechanisms:

1. **Semi-autoregressive generation.** A heavy *parallel* backbone (DFlash-style:
   one forward pass over the whole block, with target-model KV/hidden-state
   injection) produces all `γ` base logits at once, giving high first-token
   capacity. A *lightweight sequential head* then injects intra-block token
   dependency to fight the "suffix decay" / multi-modal collision that pure
   parallel drafters suffer. Two heads:
   - **Markov head** (default): a first-order transition bias `B = W1·W2`,
     low-rank (`r = 256`) — cheap embedding-lookup + logit projection.
   - **RNN head**: gated recurrent state carrying full intra-block prefix
     history; marginally better, more complex, used only at long block sizes.
   The sequential head adds only **+0.2%–1.3%** round latency over DFlash.
2. **Confidence-scheduled verification.** A small confidence head emits a
   per-position survival estimate `c_k = σ(wᵀ[h_k; W1[x_{k-1}]])`, supervised by
   the analytical acceptance rate `c*_k = 1 − ½‖p_d − p_t‖₁`. After post-hoc
   **Sequential Temperature Scaling (STS)** calibration, a **Hardware-Aware
   Prefix Scheduler** (paper Algorithm 1) chooses a *per-request* verification
   length that maximizes system throughput `Θ = τ · SPS(B)`, routing scarce
   target-verify batch capacity only toward tokens with positive expected
   return. An early-stopping rule preserves the non-anticipating property, so it
   stays lossless.

Training: the target model is frozen and shares its embedding + LM head with
the drafter; only the backbone drafter, sequential block, and confidence head
train. Objective `L = 0.1·L_ce + 0.9·L_tv + 1.0·L_conf`, position-weighted
`w_k = exp(−(k−1)/γ)`. The TV term is a direct proxy for acceptance rate
(`1 − ½‖p_d − p_t‖₁`). Trained 10 epochs on Open-PerfectBlend (1.3M prompts),
with **responses regenerated by each target model**.

### Reported results (why it matters)

- Offline accepted-length (`τ`) vs strong baselines across **Qwen3-4B / 8B /
  14B** and **Gemma4-12B** targets: **+~30% over Eagle3**, **+16–18% over
  DFlash**. A 2-layer DSpark beats a 5-layer DFlash.
- Production (DeepSeek-V4 serving, live traffic) vs the prior **MTP-1**
  baseline: **+60–85%** per-user generation speed (V4-Flash), **+57–78%**
  (V4-Pro) at matched aggregate throughput, and it removes the throughput
  cliff under strict-SLA / high-concurrency tiers.
- Storage caveat from `scripts/data/README.md`: regenerating the target cache
  is **~38 TB for the default Qwen3-4B** setting. Draft training is cheap;
  *data prep* is the heavy cost.

## Psionic current state (what's here, what's missing)

Psionic is a **pure-Rust** ML substrate that owns both **inference** and
**training** truth (no Python in the production runtime). That dual ownership is
what makes it the workspace's natural home to implement DeepSpec *ideas*
end-to-end, not just consume a checkpoint.

### Inference path — standard autoregressive, no draft+verify

- Token-by-token decode loop: `crates/psionic-serve/src/qwen35.rs`
  (`forward_token` / generate loop) and the GPT-OSS path in
  `crates/psionic-serve/src/gpt_oss.rs`. Prefill → single-token decode with KV
  reuse.
- KV cache infrastructure already exists, including **paged KV**
  (`crates/psionic-serve/src/psion_rvllm_paged_kv_manager.rs`) and a shared
  prefix store (`Qwen35SharedPrefixStore`).
- **Continuous batching** is present (`ContinuousBatchGenerationResult`,
  `run_continuous_batch_generation_requests`, `default_generation_scheduler_policy`
  in `crates/psionic-serve/src/lib.rs`).
- On-device candidate output modes already exist: `ArgmaxOnly`,
  `TopKCandidates`, `RawLogits` (`qwen35.rs`) — a partial-acceptance surface to
  build a verify step on.
- `docs/INFERENCE_ENGINE.md` (§"Text Generation Requirements", §"KV Cache
  Requirements") documents none of: block/tree verification, draft models,
  acceptance/rejection sampling, or multi-token proposal. There is **no native
  draft+verify loop** anywhere in the Rust decode path.

### The only existing "draft" surface is Apple-FM packaging metadata

- `crates/psionic-adapters/src/lib.rs`: `APPLE_FM_ADAPTER_DRAFT_MIL_FILE`
  (`draft.mil`), `APPLE_FM_ADAPTER_DRAFT_WEIGHTS_FILE` (`draft_weights.bin`),
  and `AppleFmAdapterLineageMetadata.speculative_decoding_draft_token_count`
  with `validate_draft_payload_pair(...)`.
- This is **packaging/lineage validation** for Apple's on-device Foundation
  Models adapter format (`crates/psionic-apple-fm/`), **not** a Psionic-native
  draft+verify execution path on CPU/CUDA/Metal. It does show the team already
  treats speculative decoding as an anticipated capability.

### Training path — capable, no drafter lane yet

- `crates/psionic-train/src/` is a mature lane-based trainer: actual
  pretraining (`psion_actual_pretraining_lane.rs`), Gemma4 e4b adapter SFT
  (`gemma_e4b_cuda_adapter_sft.rs`), Parameter Golf, legal DPO/SFT, Apple
  adapter experiments. Distributed collectives in `psionic-collectives` /
  `psionic-distributed`.
- No lane currently trains a **draft model for speculative decode**. But the
  ingredients DeepSpec needs are present: frozen-target supervision, LM-head
  reuse, checkpoint/resume, multi-host gradient averaging.

### Target-family overlap is strong

DSpark's evaluated targets are **Qwen3-{4B,8B,14B}** and **Gemma4-12B**.
Psionic natively serves **Qwen3.5** (primary CUDA/Metal target) and **Gemma4**
(`gemma4:e4b` dense, `gemma4:26b` sparse) — `docs/INFERENCE_ENGINE.md` §"Current
Bounded Lanes". The drafter architecture and recipe map almost directly onto
models Psionic already runs.

## Benefit assessment

**Overall: HIGH strategic relevance, HIGH implementation cost.** Psionic is the
single repo in the workspace that could implement the *whole* DeepSpec stack
natively — train the drafter (`psionic-train`) and run draft+verify
(`psionic-serve`) in Rust — for the exact model families it already serves. This
is squarely aligned with the workspace rule to *study reference repos and port
ideas into owned Rust codebases rather than vendoring external code*.

Why the benefit is real:

- **Latency is the product.** DSpark's entire thesis is lower per-user latency
  at no quality cost, under load. Psionic owns execution truth and publishes
  benchmark evidence / capability claims (`psionic-eval`); a lossless 1.5–2×
  decode speedup on Qwen3.5 / Gemma4 is directly capability-relevant.
- **The cheap design fits a from-scratch Rust port.** The Markov head is a
  low-rank (`r=256`) transition bias — implementable without a heavy second
  transformer. "A little autoregression goes a long way" (2-layer DSpark > 5-layer
  DFlash) means a modest Rust drafter can capture most of the win.
- **The substrate is already there.** Paged KV, prefix cache, continuous batch
  scheduler, and top-k candidate output modes are the exact primitives a
  block-verify loop and the hardware-aware scheduler need.

Why it is not free / honest caveats:

- **No native draft+verify loop exists.** Block proposal, single-pass batched
  verification against the target, longest-accepted-prefix sampling, KV
  rollback on rejection, and the bonus-token append all need to be built in the
  decode path. This is the bulk of the work and touches the hottest code.
- **No released checkpoint fits Psionic's targets.** DSpark publishes drafters
  only for DeepSeek-V4-Flash/Pro — not Qwen3.5 or Gemma4. To benefit on
  Psionic's own models, Psionic must *train* the drafter via the DeepSpec
  recipe, which means standing up target-response regeneration (the ~38 TB data
  step is the real cost driver, not the drafter).
- **The confidence scheduler's payoff is concurrency-gated.** Its big win is
  reclaiming wasted verify capacity under high concurrency. Psionic has
  continuous batching, but the scheduler is the most complex piece and should
  be sequenced *after* a basic lossless drafter is proven.
- **Tokenizer / sampling parity matters.** Lossless acceptance requires the
  draft and target to agree on tokenization and sampling math; Psionic's
  sampling modes (top-k/top-p/min-p/typical/mirostat) must be reconciled with
  block verification (recall Hydralisk already hit vLLM's "min_p incompatible
  with speculative decoding" constraint — see that repo's audit).

## Recommendation (phased, lowest-risk first)

1. **Spec + smallest lossless drafter, single model.** Implement a draft+verify
   decode loop in `psionic-serve` for **Qwen3.5** on one backend (CUDA or Metal)
   using the simplest possible drafter (e.g. an Eagle3-style or even a
   self-speculative/n-gram draft) to land the *verification machinery* first:
   block proposal, batched single-pass verify, longest-prefix accept, KV
   rollback, bonus token. Gate on **exact output parity** vs non-speculative
   decode (lossless) before any speedup claim. Capture in `psionic-eval`.
2. **Port the DSpark drafter (Markov head).** Add a `psionic-train` lane that
   trains a DFlash parallel backbone + low-rank Markov sequential head against a
   frozen Qwen3.5 / Gemma4 target (shared embedding + LM head, `L = 0.1·ce +
   0.9·tv + 1.0·conf`, position weighting). Reuse existing frozen-target /
   adapter plumbing. Treat target-response regeneration as a bounded, sharded
   data lane (do **not** copy DeepSpec's Python; port the algorithm).
3. **Measure `τ` and wall-clock,** position-wise, across structured (code/math)
   vs chat prompts — DSpark's gains are domain-dependent. Publish accepted-length
   and end-to-end speedup as capability evidence.
4. **Add confidence-scheduled verification last,** once a fixed-length drafter
   is proven and continuous-batch concurrency is high enough that verify waste
   is measurable. Implement the confidence head + STS calibration + the greedy
   `Θ = τ·SPS(B)` prefix scheduler with the early-stopping (non-anticipating)
   guard.

Net: DSpark is one of the highest-leverage *inference* ideas in the current
reference set for Psionic specifically because Psionic both trains and serves.
The recommended path is incremental — prove a lossless drafter on one model
before taking on the semi-AR drafter training and the hardware-aware scheduler.
