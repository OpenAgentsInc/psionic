# v0.2 Pylon Release Readiness Audit

Date: 2026-05-22

Audited checkout: `origin/main` at `fa5b824545db3005dc893d41a29cdebf10350184`

## Verdict

Do not cut a public `v0.2` release for user-distributed Pylons yet.

Psionic has credible local and loopback Pylon training evidence, signed worker
receipts, deterministic payment decision logic, Treasury/Nexus handoff schemas,
settlement-proof validation, service-mode inference installation, and several
public-network contract surfaces. That is enough for an internal canary or
release-candidate label if the release notes are explicit.

It is not enough for a user-distributed Pylon release. The release path is
blocked by unimplemented remote Pylon dispatch, unproven live payout execution,
failing public-network/payment contract checkers, missing v0.2 package identity,
and incomplete Pylon-specific telemetry enforcement.

## Scope

This audit answers four questions:

- Can users install and run Pylons?
- Will remote Pylon training work outside local/loopback execution?
- Are payments actually working?
- Are we collecting enough telemetry to operate and debug distributed Pylons?

The audit intentionally separates Psionic's inference mesh lane from the Qwen
legal training Pylon lane. `psionic-mesh-lane` is a real installable service
entrypoint for durable inference mesh nodes. It does not prove public Qwen
legal Pylon training dispatch, user payout settlement, or public-testnet
readiness.

## Blocking Findings

### 1. Remote Pylon dispatch is not implemented

`QwenLegalPylonDispatchMode` names `Tailnet` and `Production`, but the dispatch
function blocks anything that is not `Loopback` or `LocalOnly`:

- `crates/psionic-train/src/qwen_legal_pylon_dispatch.rs:275` checks the mode.
- `crates/psionic-train/src/qwen_legal_pylon_dispatch.rs:282` records
  `BlockedModeNotImplemented`.
- `crates/psionic-train/src/qwen_legal_pylon_dispatch.rs:379` returns
  `remote transport must be admitted before worker execution` for Tailnet and
  Production.

Release impact: users cannot receive and execute real remote Pylon training
jobs through the Qwen legal Pylon dispatcher. A user-distributed release would
mostly install software that cannot participate in the intended public Pylon
workflow.

Minimum gate:

- authenticated remote job envelope transport
- remote worker execution path
- retry, timeout, and duplicate-shard behavior over real network failure
- receipt upload path
- artifact upload path
- operator-visible dispatch status and failure classification

### 2. Payments are not proven as live payouts

The payment model is substantial but not yet sufficient for the release claim
"payments working."

What exists:

- `crates/psionic-train/src/qwen_legal_pylon_training_job.rs:1199` attaches
  returned Treasury/Nexus settlement proofs to closeout.
- `crates/psionic-train/src/qwen_legal_pylon_training_job.rs:1280` marks the
  promotion payment gate as `PaymentSettled`, `DeferredByOperator`, or
  `Blocked`.
- `crates/psionic-train/src/qwen_legal_pylon_training_job.rs:1479` validates
  settlement proofs, including proof digest, amount, live settled proof time,
  payment hash or transaction proof, and wallet-secret redaction.
- Payment unit tests pass.

What is missing:

- no Psionic-owned live wallet send path was found
- no retained end-to-end live small-value payment run was found for distributed
  Pylons
- the real Qwen rehearsal reports `payment gate: DeferredByOperator`
- public settlement and reward checkers are currently failing

Release impact: Psionic can produce payable decisions and validate returned
proofs. It cannot honestly claim user payouts are working end to end until a
Treasury/Nexus live settlement run is retained and the publication fixtures are
stable.

Minimum gate:

- at least one live small-value Bitcoin/Lightning payout from an accepted Pylon
  job
- retained proof with payment hash or chain transaction proof
- reconciliation against the handoff batch and worker receipt digest
- failed, pending, duplicate, and withheld payment cases visible to operators
- no wallet secret material in any retained artifact

publication evidence cannot be used as a green v0.2 gate today.

Minimum gate:

- regenerate canonical fixtures
- make every checker above pass from a clean checkout
- add these scripts to the v0.2 release checklist or CI gate

### 4. v0.2 release identity does not exist yet

The root workspace package still says:

- `Cargo.toml:87` -> `version = "0.1.1"`
- `Cargo.toml:91` -> `publish = false`

`git tag --list 'v*'` returned no v-prefixed tags in the audited checkout.

Release impact: there is no actual v0.2 artifact identity for operators to pin,
verify, or upgrade from.

Minimum gate:

- decide whether v0.2 is source-only, binary tarball, container image, crate
  release, or internal signed release bundle
- bump version or define release manifest identity
- publish checksums, SBOM or dependency inventory, and build command
- tag `v0.2.0` only after release checks pass

### 5. Pylon telemetry is not enough for user distribution

Generic telemetry exists:

- `docs/TOKIO_RUNTIME_TELEMETRY.md` documents optional Tokio runtime telemetry.
- `crates/psionic-observe` provides the runtime builder and env-driven config.
- `docs/PSION_EXECUTOR_MANDATORY_LIVE_METRICS.md` defines an 11-metric executor
  packet with loss, exactness delta, held-out delta, throughput, latency,
  checkpoint latency, gradient posture, memory headroom, device health,
  dataloader stalls, and recovery latency.

But the Pylon worker receipt currently only inserts:

- `input_artifact_count`
- `output_artifact_count`
- `runtime_ms`

See `crates/psionic-train/src/qwen_legal_pylon_training_job.rs:935`.

Release impact: if user Pylons fail, throttle, overheat, stall, run out of
memory, stop uploading artifacts, or fail payment reconciliation, the current
Pylon receipt surface is too thin to diagnose the system from retained
telemetry alone.

Minimum Pylon telemetry gate:

- job lifecycle: queued, assigned, accepted, started, heartbeat, completed,
  failed, retried
- progress: step, examples, tokens, loss, grad norm or clipping, eval probe
- hardware: CPU, RAM, VRAM or unified memory, disk, accelerator name, driver
  posture, temperature or throttle posture where available
- performance: tokens/sec, examples/sec, step latency, checkpoint latency,
  upload latency, receipt latency
- network: peer endpoint, bytes sent/received, reconnects, dispatch latency,
  artifact upload latency
- payment: payable, withheld, pending, settled, deferred, failed,
  payout_authorization_id, proof status
- failure taxonomy: validation failure, transport failure, resource failure,
  payment failure, artifact digest drift, duplicate shard
- retention: local log hash, redacted logs path, telemetry packet digest,
  upload status

### 6. Production key custody is not proven for Pylons

Signed receipts exist, but the local worker path uses deterministic worker
signing keys derived from worker and job identity:

- `crates/psionic-train/src/qwen_legal_pylon_training_job.rs:901`

That is acceptable for fixtures and deterministic tests. It is not sufficient
as the production key-management story for user-distributed Pylons.

Minimum gate:

- Pylon identity issuance
- local private-key storage guidance
- rotation and revocation
- lost-device handling
- receipt verification against registered identities
- replay and duplicate prevention across real dispatch windows

## Release Recommendation

Cutting `v0.2.0` now would overclaim. The honest next release label is one of:

- `v0.2.0-alpha.1`: local/loopback Pylon evidence, deferred payment closeout,
  installable inference mesh lane, no public user payouts
- `v0.2.0-rc.1`: only after remote Tailnet Pylon dispatch works with a trusted
  canary node and at least one live small-value payment proof is retained

Do not distribute Pylons to normal users until all of these are true:

1. `Tailnet` or `Production` Pylon dispatch runs a remote worker end to end.
2. A clean machine can install, register, receive a Pylon job, execute it,
   upload artifacts, upload receipt, and appear in the operator status surface.
3. A live small-value payout settles and is reconciled against the retained
   worker receipt and handoff batch.
4. Pylon telemetry includes the mandatory operational fields listed above.
5. Public registry, bootstrap, explorer, testnet, reward, settlement, curated,
   open, and incentivized run contract checkers pass from a clean checkout.
6. A v0.2 release manifest, version identity, build digest, checksums, and tag
   exist.
7. The release notes state exactly what execution classes are supported and
   what remains canary-only.
